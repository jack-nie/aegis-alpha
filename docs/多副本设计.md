# 编排器多副本设计（P4-16，评审 R10）

> 状态：**只做了接口和文档，没有引入新依赖**。Postgres / Redis 后端都标为「待确认」：需要人工批准新增依赖之后才实现。

## 1. 现状：哪些状态只存在于单个进程里

| 状态 | 位置 | 多副本下的问题 |
|---|---|---|
| LangGraph checkpoint（审批中断、恢复） | `AsyncSqliteSaver`，存在本地文件 `data/checkpoints.db`（`main.py` lifespan） | `/resume-workflow(-stream)` 如果打到别的副本，会找不到 checkpoint，结果是恢复失败或从头再跑 |
| steering / follow-up 队列 | `MessageQueueRegistry`，在进程内存里（`dependencies.message_queues`） | `/message-queue/*` 打到别的副本会返回 `NOT_ACTIVE`；Java 侧会退回到普通路由 |
| 取消标记 | `RunRegistry`，在进程内存里（`WorkflowEngine._runs`） | `/cancel-run` 打到别的副本会返回 `NOT_ACTIVE`。Java 的 CAS 终态仍然以 Java 为准，但 Python 会继续跑到结束 |
| 线程元数据、图缓存 | `WorkflowEngine` 的内存字典 | 只影响性能和清理，不影响正确性 |

不变的原则：**Java 是 run 状态的唯一真相源**（CAS 写终态）。Python 副本只负责执行，并尽力上报事件。

## 2. 本阶段落地的接口（`app/core/run_backends.py`）

- `RunQueueBackend`（Protocol），方法有 `enabled`、`open_run`、`get`、`enqueue`、`finish_run`。现有的 `MessageQueueRegistry` 已经满足这个接口，由 `run_queue_backend_from_settings` 选择。共享实现必须保持以下契约：
  - `open_run` 幂等；恢复时重新激活。
  - `enqueue` 校验归属（`OWNER_MISMATCH`），拒绝已关闭的 run（`NOT_ACTIVE`）。
  - 每条消息最多投递一次；只在执行该 run 的副本上 drain。
  - `finish_run` 返回未投递的消息。
- `CheckpointerFactory`（Protocol），包含 `name`、`durable`、`shared`、`async open()`、`async close()`。现有实现：
  - `SqliteCheckpointerFactory`：持久，但不能在副本间共享。这是默认值，行为和以前一样。
  - `MemoryCheckpointerFactory`：只用于测试和演示，重启后丢失。
- 配置项（都有默认值，默认行为不变）：
  - `AEGIS_ALPHA_CHECKPOINTER_BACKEND=sqlite|memory`
  - `AEGIS_ALPHA_RUN_QUEUE_BACKEND=memory`
  - `AEGIS_ALPHA_REPLICAS=1`
- 配置成 `postgres` 或 `redis` 时，启动直接抛 `BackendUnavailable`，**不会静默降级到本地后端**。
- 如果 `REPLICAS>1`，但用的仍是本地后端，启动时打印 `[REPLICAS]` 告警，提示需要按 runId 做粘性路由。

## 3. 目标形态（待确认，需要新增依赖）

1. **checkpoint**：用 `langgraph-checkpoint-postgres`（`AsyncPostgresSaver`），复用现有 Postgres 或单独建库。`PostgresCheckpointerFactory` 设置 `shared=True`。迁移旧的 SQLite 线程时，只需要迁移状态为 PAUSED 的 run；完成的线程可以丢弃（默认 `workflow_cleanup_checkpoints=false`，待确认）。
2. **队列和取消**：用 Redis 实现 `RedisRunQueueBackend`：
   - 每个 run 一个 list/stream，外加 `owner` hash。
   - 取消标记用 key + pub/sub，执行副本订阅 `cancel:{runId}`。
   - drain 用 `LMPOP` / `XREADGROUP` 保证至多一次。
   - 设置 TTL，等于 workflow 超时加上宽限时间。
   - `RunRegistry` 需要同样抽象出一个 `RunControlBackend`（本阶段没有拆，见第 5 节）。
3. **过渡方案（不需要新依赖）**：在网关或 Java 侧按 `runId` 做粘性路由，把 `/stream-workflow`、`/resume-*`、`/message-queue/*`、`/cancel-run` 都路由到同一副本。checkpoint 放在共享卷上，单写者。

## 4. 验证计划

- 契约测试（`tests/test_run_backends.py`）对任何实现都要通过：归属校验、关闭后拒绝、幂等打开、`finish_run` 返回未投递消息。
- 引入 Redis 或 Postgres 后，把同一组测试参数化跑在新后端上，用 docker-compose 起服务。再加一条跨进程用例：A 进程执行，B 进程入队或取消，A 能收到。

## 5. 已知限制

- `RunRegistry`（取消标记）还没有抽象成接口，因为它与 `await_or_cancel` 的 asyncio Event 耦合。要抽象，需要把等待改成「本地 Event + 远端订阅」。
- 图缓存和线程元数据仍然是进程内的；它们只影响性能，不影响正确性。
