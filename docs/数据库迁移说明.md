# 数据库迁移说明（决策：迁移保持人工执行）

> 本轮决策（见仓库外的 `待确认项决策与修改说明.md`）：不新增任何数据库迁移；P3-14 唯一索引和 `user_id/tenant_id` 的 ALTER **保持人工控制**。本文件说明它们现在到底由谁、在什么时候执行，避免误解。

## 1. 启动时会自动执行什么

| 机制 | 何时执行 | 内容 | 开关 |
|---|---|---|---|
| `spring.sql.init`（`classpath:db/mysql/schema.sql`） | 每次 API 启动 | `CREATE TABLE IF NOT EXISTS ...`；文件末尾的增量 ALTER：`chat_thread.user_id/tenant_id`、`workflow_run.user_id/tenant_id`、索引 `idx_workflow_run_owner` | `AEGIS_ALPHA_SQL_INIT`，默认 `always`；`continue-on-error: true`，所以已存在的列/索引报错会被忽略 |
| `SchemaMigrationRunner`（CommandLineRunner） | 每次 API 启动 | 只做「缺列就加」的增量列（`workflow_run.completed_at` 等）和若干建表 | 不受 `AEGIS_ALPHA_SQL_INIT` 控制 |
| `db/mysql/migrations/P3-14-workflow-run-idempotency-unique.sql` | **从不自动执行** | 把 `idx_workflow_run_idempotency` 换成唯一索引 | 只能由 DBA 手工执行 |

**注意**：`user_id/tenant_id` 的 ALTER 写在 `schema.sql` 里。默认配置（`AEGIS_ALPHA_SQL_INIT=always`）下，它们会在启动时自动尝试执行（只加可空列和普通索引，不改数据）。如果你的环境要求所有 DDL 都由人工审核后执行：

1. 设置 `AEGIS_ALPHA_SQL_INIT=never`；
2. 由 DBA 手工执行 `schema.sql` 末尾「Incremental upgrades」一节的 5 条语句（已执行过的会报 duplicate column/index，可忽略）；
3. `SchemaMigrationRunner` 的增量列仍会自动补齐；如需完全人工控制，需要另行改造（本轮不做）。

## 2. P3-14：workflow_run 幂等唯一索引（人工）

前置条件和步骤都写在脚本里：

1. 先执行第 1 步的查询，确认没有重复的 `(workflow_key, subject, idempotency_key)`；
2. 如有重复，按库评估后再决定是否执行第 2 步（注释掉的清理语句：保留最早一条，其余置空 key，历史保留）；
3. 执行第 3 步换索引。

未执行 P3-14 时，应用层的查重（`coalesce(subject,'')`）和跨用户 key 拒绝仍然生效，只是并发竞争下数据库不兜底。

## 3. 本轮明确不做的迁移

- 用量（cache / reasoning / cost）**不落库**：继续保存在 run 的 trace JSON / `final_state` 里（决策 D8）。
- `chat_message` **不加** provider 列：provider 记录在 run event 里（决策 D8）。
- 旧消息 ID 的排序问题用查询排序规则解决（决策 D10c），不加序列列。
